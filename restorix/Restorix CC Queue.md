## Prompt 628 — Setter Activity: add a Closer leaderboard tab, move the invite trigger to a floating bottom-right bubble, closers can now invite closers too

**Why:** Brayden wants closers to be able to see what OTHER closers are doing, not just setters, from this same page — plus a layout rework of the toolbar and the invite trigger to match patterns already established elsewhere in the app.

**Where:** `src/pages/SetterActivity.jsx` (all of the layout/tab work), `src/hooks/useInvites.js` + `supabase/functions/send-invite-sms/index.ts` + its RLS policy (the invite-role expansion — see below, this is the one part of this prompt that touches backend security surface, not just UI).

**What to do:**

1. **New Setter/Closer view toggle, boxed pill style (reuse `PillToggle`, same as Training's Script/Videos).** Place it where the existing Daily/Monthly/All Time `PillToggle` currently sits (top-left of the toolbar row); the existing Daily/Monthly/All Time toggle + its paginator (`DayPaginator`/`MonthPaginator`/`CustomDatePicker`) moves down to a **new row directly below it**, same left alignment. Default view: Setter (unchanged from today).

2. **Closer leaderboard.** When the new toggle is set to "Closer," swap the table's data source and columns:
   - Reuse `statsForCloser(leads, closerId, start, end)` from `src/hooks/useStats.js` (already exists, already computes `{assigned, pending, noShow, lost, closed, closeRate, noShowRate}` for a closer over a period — this is the exact real per-closer performance logic Overview/Commissions already use, don't reinvent it) instead of `statsForUser`.
   - Filter `useReps()`'s result to `role === 'closer'` instead of `'setter'` for this tab.
   - Columns, mirroring the Setter table's shape (Name + 3 metric columns): **Name / Booked (`assigned`) / Closed (`closed`) / Close Rate (`closeRate`)**. `closeRate` already comes back as a formatted string like `"62%"` or `"—"` (see `pct()` in useStats.js) — render it as-is, don't reformat.
   - Same loading/empty states, same row styling, as the existing table.

3. **Toolbar's right side: date navigator moves to where "Invite Setter" used to be** (top-right of the first row, next to/above where the button was). The button itself leaves the toolbar entirely — see next point.

4. **Invite trigger becomes a floating bottom-right bubble**, same pattern as `MyLeads.jsx`'s `RequestLeadsBubble` (`fixed bottom-6 right-6 z-30`, `h-14 w-14 rounded-full shadow-lg`, dismissible first-load tooltip callout) — reuse that structure/classes, swap its icon back to `Send` (this page's existing invite icon) and its accent color to match this page's own button styling rather than `RequestLeadsBubble`'s status-new color.

5. **The invite modal gets two tabs, Setter and Closer** (another `PillToggle` inside the modal, or two simple tab buttons at its top) — same phone-number form underneath either way, just targeting a different role. **This requires a real backend change, not just UI**, since today closers can only ever invite setters:
   - `invites_insert_closer` RLS policy currently restricts closer-created invite rows to `role = 'setter'` only — widen it to also allow `role = 'closer'`.
   - `send-invite-sms`'s `requireCloser`/token-reverification logic hardcodes checking the invite row's `role = 'setter'` before sending — widen that check to accept either `'setter'` or `'closer'`, and pass the actual chosen role through from the client instead of assuming setter.
   - `useSendSetterInviteSms` (`useInvites.js`) needs to accept a `role` param (`'setter' | 'closer'`) instead of hardcoding `role: 'setter'` in the invite-row insert — rename it to something role-agnostic (e.g. `useSendRepInviteSms`) if that's cleaner, updating its one call site.
   - Copy inside the modal should say "Text a new setter/closer a link..." matching whichever tab is active.

6. **Make the table box taller.** It's currently a hardcoded `h-[547px]` (Prompt 606's own comment already flags this as a best-guess, never live-verified against a real window). There's visibly empty space below it at normal viewport sizes — grow it by a reasonable amount (something in the 650–700px range is a reasonable starting point) and flag in your shipped note, same as 606 did, that this still needs a real human eyeballing it against an actual screen rather than being treated as exact.

**Verify, don't guess:** Confirm the Setter tab's numbers are byte-for-byte unchanged from today (same `statsForUser` call, just relocated). Confirm the Closer tab's numbers match `statsForCloser`'s real output for at least one closer, hand-traced against the live `leads` table the same way Prompt 581 verified this function originally. Confirm the RLS policy change is scoped narrowly (closers can create `setter` or `closer` invite rows for themselves, nothing broader — re-check `invites_insert_closer`'s full definition before and after). Confirm `send-invite-sms` actually rejects a token whose role doesn't match what's being requested (the re-verification check should still be meaningful, not silently permissive). Confirm the floating bubble doesn't overlap/collide with anything else fixed-positioned on this page. `npm run build`/`npm run lint` clean. **Per the standing instruction: "shipped" means the Vercel production deployment for this commit reaches `READY` and the live site's domain alias actually serves it — check this directly via Vercel MCP tools, not a local build pass.**

**Scope check before shipping:** No changes to `statsForUser`/`statsForCloser`'s own logic — reuse both exactly as they exist. No changes to `MyLeads.jsx`'s own `RequestLeadsBubble` (only reference its pattern, don't extract/share the component unless that's genuinely trivial and risk-free).
