## Prompt 617 — Zoom connect flow: add a Disconnect option, and stop leaving the portal to connect (popup instead of full-page redirect)

**Why:** Two things Brayden hit directly while testing the just-fixed Zoom connect flow (Prompt 615/616-adjacent bugfix, shipped this session outside the numbered queue — see [[Restorix Memories]] for the live debugging session that found the real root cause: a missing `user:read:user` granular scope on the Zoom app). First: once `closer_zoom_tokens` has a row for a closer, Settings only ever shows "Connected" — there's no way to disconnect and reconnect a different Zoom account, or to recover if a token gets into a bad state (this session had to delete the row directly in Supabase to force a retest, which isn't something Brayden can do himself). Second: clicking "Connect Zoom" today does `window.location.href` to `zoom.us/oauth/authorize`, which fully navigates the browser away from the portal — Brayden's explicit ask: "I don't want you to leave the Restorix portal... a pop-up come up or somehow you could just do it within the portal."

**Constraint to work within:** Zoom's OAuth consent screen itself cannot be embedded in an iframe — like virtually every OAuth provider, Zoom blocks framing (clickjacking protection), so an iframe isn't an option for the authorize/consent step specifically. A popup window (`window.open`) that completes the OAuth round-trip and closes itself is the standard workable pattern here, and satisfies "never leave the portal" in the sense that matters — the portal tab itself never navigates away.

**Where:**
- `src/pages/Settings.jsx` — `ZoomForm`, `useZoomConnection`, `useConnectZoom` (Prompt 530) — today's `window.location.href = data.url` full-page redirect lives here.
- `supabase/functions/zoom-oauth-start/index.ts` — unchanged, still returns the authorize URL.
- `supabase/functions/zoom-oauth-callback/index.ts` — after Zoom redirects back here with the auth code and this function finishes the token exchange, it currently redirects the browser somewhere (read it to confirm exactly where before changing it). This is the piece that needs to become popup-aware.
- New: a way to remove a closer's own `closer_zoom_tokens` row — check whether RLS already permits a closer to `delete` their own row (`closer_id = auth.uid()`); if so, a direct Supabase client call is enough and no new edge function is needed. If RLS doesn't already allow it, add the narrowest fix (either a policy, or a small `disconnect-zoom` edge function using the service role) — CC's call on which is the smaller, safer diff.

**What to do:**

1. **Popup instead of full-page navigation.** In `useConnectZoom`, after fetching the authorize URL from `zoom-oauth-start`, open it via `window.open(url, 'zoom-connect', 'width=520,height=720')` instead of `window.location.href = url`. If the popup is blocked (returns `null`), fall back to the current full-page redirect with a brief note in the UI — don't leave the user stuck with a silent no-op.

2. **`zoom-oauth-callback` becomes popup-aware.** After it completes the token exchange and stores the tokens (unchanged), instead of just redirecting, have it return a tiny self-contained HTML page that does `window.opener.postMessage({ type: 'zoom-oauth-result', ok: true }, '<the real portal origin>')` (or `ok: false` + an error message on failure) and then `window.close()`. Use an explicit target origin, never `'*'` — hardcode the portal's real origin the same way `ZOOM_REDIRECT_URI` is already hardcoded in `zoom-oauth-start`. Keep a plain-redirect fallback for the case there's no `window.opener` (e.g. someone opens the callback URL directly, or a browser that already closed the opener) — CC's call on the safest fallback destination (Settings page is reasonable).

3. **Settings listens for the result.** `ZoomForm` (or `useConnectZoom`) adds a `message` event listener while the popup is open, checks `event.origin` matches the expected Supabase functions origin before trusting it, and on `ok: true` refetches `useZoomConnection`'s status (so "Connect Zoom" flips to "Connected" without a manual page reload) and closes/cleans up. Also poll `popup.closed` (e.g. every 500ms) so if the user closes the popup manually without finishing, the UI just quietly resets — no error toast for a plain cancel.

4. **Disconnect button.** When connected, show a "Disconnect" action next to the "Connected" state. On click, remove the closer's `closer_zoom_tokens` row (via whichever path step "Where" above settled on), then refetch connection status so the UI reverts to showing "Connect Zoom". No confirmation dialog needed — this only affects the acting closer's own connection, nothing destructive to anyone else's data, and reconnecting is one click away.

**Verify, don't guess:** Since this session's tool-safety rules block entering a password, live click-verification isn't possible here either — same standing caveat as every prompt since 609. Do as much real verification as the code allows: confirm the callback's `postMessage` target origin is the literal real portal origin, not `'*'`; confirm the Settings-side listener checks `event.origin` before trusting the message; confirm the disconnect path actually deletes the row (test via direct SQL against a scratch row, not the live Test Closer account, if verifying end to end) and that reconnecting afterward doesn't collide with a leftover row (upsert semantics, not a bare insert that could conflict). Read `zoom-oauth-callback`'s current redirect behavior in full before changing it — don't assume its current shape.

**Scope check before shipping:** No change to `create-zoom-meeting` or `get-zoom-personal-room`. No change to the Zoom Marketplace app configuration itself (already fixed live this session — scopes, redirect URLs). Doesn't touch Meeting Room's own Join buttons — that's Prompt 618, a separate and much bigger piece of work. Popup-blocked fallback exists and doesn't silently fail.

## Prompt 618 — Embed the actual Zoom call inside the Meeting Room tab via the Zoom Meeting SDK (Phase 3, explicitly deferred by Prompt 615)

**Why:** Brayden's explicit ask, watching Meeting Room work for the first time: "the meeting room, I want the meeting room to work the same way [as the popup connect flow]... I would rather an iframe or something open up on the Meeting Room tab and you just do it there... so you don't leave the portal." Today, both join actions (Personal Meeting Room, booked-call Join) are plain `target="_blank"` links that open the real Zoom app/website in a new tab — exactly what Prompt 615 scoped, with an explicit note that in-page embedding was out of scope until Phase 3, "blocked on registering a separate Zoom Meeting SDK app." This prompt is that Phase 3 work.

**This is a genuinely different integration from everything shipped so far — read this whole section before starting, don't treat it as a small addition:**

- Everything Zoom-related shipped to date (`zoom-oauth-start`/`callback`, `create-zoom-meeting`, `get-zoom-personal-room`) uses Zoom's **OAuth + REST API** — the "Restorix Portal" app in Marketplace, a **User-managed app**, with its own Client ID/Secret. That app and those credentials are NOT reused here.
- Embedding a live call in a web page requires Zoom's separate **Meeting SDK** (`@zoom/meetingsdk` npm package, a client-side JS SDK that renders the call inside an element on the page), which authenticates via its own **SDK Key/Secret** issued by a **Meeting SDK app** — a different app type in the Zoom Marketplace, registered separately from the existing OAuth app. **This does not exist yet and is a hard blocker** — flag back immediately (don't improvise a workaround) if it isn't already set up when this prompt starts. Brayden or this session can register it; either way the resulting SDK Key/Secret need to land as new Supabase secrets (`ZOOM_SDK_KEY`/`ZOOM_SDK_SECRET`) before any of this can be tested end to end.
- Joining a meeting via the SDK requires a **signed JWT** ("signature"), generated **server-side** (never in the browser, since it needs the SDK Secret) per join attempt, encoding the meeting number, role (0 = attendee, 1 = host), and an expiry. This is a new edge function, not something bolted onto an existing one.

**Where:**
- New Supabase secrets: `ZOOM_SDK_KEY`, `ZOOM_SDK_SECRET` (from the new Meeting SDK app — cannot be set by this session; flag back for Brayden to set via the Supabase dashboard, or hand him/CC the exact `supabase secrets set` command, once the SDK app exists).
- New edge function, e.g. `zoom-sdk-signature` — takes a meeting number + intended role, returns a signed JWT. Authed closer only (`verify_jwt: true`), same identity-resolution pattern as `get-zoom-personal-room`.
- `src/pages/MeetingRoom.jsx` (Prompt 615) — both join actions (`Start Your Meeting Room`, each booked call's Join button) change from `<a target="_blank">` to something that fetches a signature from the new function and initializes the SDK client in-page.
- `create-zoom-meeting`'s stored `zoom_join_url` — check whether the meeting number/password needed for an SDK join can be parsed out of the stored join URL, or whether `create-zoom-meeting`'s own response needs to be widened to store the raw meeting `id`/`password` fields separately (likely needed — a join URL alone isn't the cleanest input for the SDK's `client.join()` call, which wants a bare meeting number + password). Same question applies to the Personal Meeting Room's `pmi`/`personal_meeting_url` from `get-zoom-personal-room`.
- New client dependency: `@zoom/meetingsdk` (check bundle size impact — it's not small; consider dynamic `import()` so it only loads when a closer actually opens Meeting Room, not on every page load).

**What to do:**

1. **Confirm the Meeting SDK app and its secrets exist** before writing any embed code. If they don't, stop here and flag it back rather than guessing at credentials or stubbing around the gap.
2. **New `zoom-sdk-signature` edge function** generating the SDK JWT server-side per Zoom's documented signature format (algorithm, required claims, expiry) — read Zoom's current Meeting SDK auth docs directly rather than assuming the shape hasn't changed.
3. **Wire the join UI.** Replace both external links with an in-page container (a dedicated modal or an expanding section within Meeting Room — CC's call on the cleaner layout) that, on click: fetches a signature for that specific meeting, dynamically imports `@zoom/meetingsdk`, and calls its join method with the meeting number/password + signature + SDK key + the closer's display name. Handle join failure visibly (bad/expired signature, meeting not started yet, etc.) rather than a silent blank embed.
4. **Leaving a call** needs an explicit, obvious exit back to the normal Meeting Room view (the SDK typically takes over a chunk of the page) — don't leave a closer stuck in an embedded call view with no way back to the rest of the portal.
5. Leave `create-zoom-meeting`'s and `get-zoom-personal-room`'s existing behavior intact for any caller still expecting a plain URL — widen their responses rather than breaking the shape those functions already return.

**Verify, don't guess:** This is the single hardest thing to verify blind of everything shipped so far — an embedded live call cannot be meaningfully confirmed without an actual two-party Zoom call in progress, which this session cannot arrange. Do everything that IS verifiable without that: confirm the signature function's JWT decodes correctly (structure/claims) via a standalone check; confirm the SDK's documented required parameters are all being passed; confirm the dynamic import actually keeps `@zoom/meetingsdk` out of the main bundle (check the build output); confirm the exit-the-call control is reachable in the DOM even without a live meeting. Flag explicitly and clearly in the shipped notes that the actual join-a-real-call path is unverified and needs a real two-person test before Brayden relies on it with an actual client.

**Scope check before shipping:** No change to the existing OAuth app or its credentials. No change to Prompt 617's connect/disconnect popup flow. If the SDK app/secrets aren't ready, this prompt does not proceed on guessed credentials — it stops and flags back instead.
