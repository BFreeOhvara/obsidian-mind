**Prompt 437 — full portal restructure shipped 2026-08-16/17, committed and pushed** (`e5d3fab`, on top of `6747e6a`, confirmed on GitHub main). The big one: role-specific Overview, a real lead-recycling pipeline ported from Ohvara's dead legacy system, and a nav restructure. Full detail worth keeping since this reshapes the whole app:

- **Legacy research, done right:** rather than reading 20+ migration files by hand, pulled the live, final function/trigger/cron definitions directly from `ohvara-dashboard`'s actual Supabase project (`jjextitmbptoaolacocs`) — Postgres functions get replaced via `CREATE OR REPLACE`, so the live DB has the consolidated final version regardless of migration history. Found the real design: `assign_daily_batches()` (SQL function, pg_cron every 15min) tops up each rep's pool from the unassigned pool; a `redistribute-no-answers` edge function (cron every 5min) returns 24h-cooled-down leads to the pool (though the legacy version doesn't guarantee a *different* rep — it just nulls `assigned_rep_id` and lets the next batch-assign pick whoever needs leads, which could theoretically be the same person); `assign-closer` edge function does round-robin via a `closer_rotation` table ordered by `last_assigned_at`.
- **Deliberate deviations from the legacy pattern, not blind copies:** (1) Brayden's spec explicitly requires no-answer redistribution NEVER goes back to the same setter — legacy doesn't guarantee this, Restorix's `redistribute_no_answers()` does, via an explicit `id is distinct from original_setter_id` exclusion. (2) Built everything as pg_cron calling SQL functions directly (`select my_function()`) rather than legacy's cron→edge-function→pg_net→HTTP→service-role-client indirection — simpler, no `pg_net`/service-role-key config needed, appropriate for Restorix's smaller scale. (3) No `closer_rotation` table — round-robin state lives directly on `profiles.last_closer_assignment_at`, avoiding a parallel table that can drift out of sync with real profile rows.
- **Schema (all via `apply_migration` on `avgvmzshujwphneykuvu`):** status enum renamed `callback`→`follow_up`, `booked`→`appointment_booked` (`ALTER TYPE ... RENAME VALUE`, preserves existing rows); `callback_at`→`follow_up_at` column rename; new `assigned_setter`, `no_answer_at`, `last_action_by`, `last_action_status`, `last_action_at` columns on `leads`; new `last_closer_assignment_at` on `profiles`; new `no_answer_queue`/`follow_up_queue` tables (admin-only RLS select, no client write path — only the trigger/functions touch them). **Tightened `leads` RLS**: insert is now admin-only (setters no longer add leads — this needed explicit user confirmation via AskUserQuestion since it's a real permission narrowing, not just an additive change); update is admin-or-`assigned_setter=auth.uid()` (previously any setter could edit any lead).
- **Pipeline logic:** one trigger function (`handle_lead_pipeline`, fired by `leads_pipeline_trigger`) handles all four immediate status-change side effects (no_answer/follow_up/not_interested/appointment_booked → each clears `assigned_setter`, stamps `last_action_by/status/at`; appointment_booked also does the round-robin closer assignment inline, no separate function/cron needed since it's immediate not time-delayed). Three cron-scheduled SQL functions: `assign_setter_batches(pool_size=150)` (*/15 min), `redistribute_no_answers()` (*/5 min, enforces the different-setter rule), `process_follow_up_returns()` (hourly, returns to the *same* setter). All four functions had public/anon/authenticated EXECUTE revoked after `get_advisors` flagged them as directly callable via REST RPC — a real security gap (anyone could have called `redistribute_no_answers()` on demand via the API), fixed immediately, not left for later.
- **A bug in my own migration, caught before shipping:** first version of `statsForUser` (Stats page) kept filtering on `created_by`/current `status` — but leads are now always admin-`created_by`, and the pipeline's own automated cycling (redistribution, follow-up returns) resets `status` back to `'new'` well after a setter's action, silently zeroing out their historical stats. Caught this by actually checking the rendered Stats page after building (showed 0/0/0% for an account that had definitely logged calls), traced it to the stamps not existing yet at the time those particular test rows were touched, then fixed properly with the `last_action_*` columns (frozen at the moment of the setter's action, never touched again by later pipeline activity) rather than papering over it.
- **Verified thoroughly against the real backend, not just built-and-hoped:** ran the full pipeline by hand via direct SQL — pool assignment respects the cap and backfills correctly (tested with `pool_size=3` to make the mechanism observable without needing 150+ fake rows); no-answer correctly blocks redistribution within the 24h window (0 processed) then correctly redistributes to a genuinely *different* setter once backdated past the cutoff; follow-up correctly holds a lead for the *same* setter until backdated past its due date; not-interested correctly clears the pool slot with zero queue-table entries (true terminal state); booked leads round-robin alternated cleanly across two closers (closer→closer2→closer). Re-ran the full sequence a second time after adding the `last_action_*` columns to confirm the fix didn't regress any of the mechanics.
- **Real-user rendering verified for setter and closer** via the same session-token-injection technique from Prompt 436 (browser password-field entry is still blocked by the permission classifier, confirmed yet again) — confirmed correct pool contents, correct nav gating (setter: no Queue/Users; closer: no Queue/Users), Training's 3 tabs all render and switch correctly, Stats shows accurate numbers post-fix. **Also verified the RLS tightening is a real server-side boundary, not just a client redirect illusion** — attempted a raw `curl PATCH` as the setter against a lead assigned to a different setter (silently no-opped, 0 rows affected) and against their own lead (succeeded) — confirms the policy actually enforces, not just the UI hiding the button.
