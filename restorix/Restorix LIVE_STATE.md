**Prompt 501 — Dark mode scoping doc for `restorix-portal`, delivered 2026-08-20, planning only — nothing implemented, awaiting Brayden's review before any build work starts.**

Findings below are grounded in the actual codebase (file/line references, real counts), not a generic dark-mode checklist.

**1. Token/CSS-variable strategy.** The foundation is already close to dark-mode-ready: every color in `src/index.css` is a `:root`-scoped CSS custom property (`--bg-base`, `--bg-surface`, `--bg-elevated`, `--bg-muted`, `--text-primary`, `--text-secondary`, `--text-faint`, `--accent`/`-bright`/`-deep`, `--border`, `--danger`, `--success`), piped through `tailwind.config.js`'s `theme.extend.colors` as `base`/`surface`/`elevated`/`muted`/`fg.*`/`accent.*`/`line`/`danger`/`success`. A dark theme means redefining these same 13 variables under a dark selector — no new token names, no new Tailwind classes for the ~35 components/16 pages that already consume them. Two concrete prerequisites: (a) `tailwind.config.js` currently has no `darkMode` key, which means Tailwind defaults to the `media` strategy (pure OS-preference, no manual override possible) — needs `darkMode: 'class'` (or `'selector'`, both supported on the installed `tailwindcss: ^3.4.19`) added before a manual toggle can work at all; (b) the project's own known "opacity-modifier utilities are inert" bug (this project's standing gotcha, hit and worked around three separate times — Prompt 477/489/491 — because `base`/`surface`/`elevated`/`muted`/`fg.*`/`line` are defined as plain `var(--x)` strings rather than the `rgb(var(--x-rgb) / <alpha-value>)` form only `accent`/`danger`/`success` use) means any dark-mode work touching those six tokens' opacity-modified usages (e.g. a hypothetical `bg-base/80`) will silently no-op exactly like it already does today — not a new risk, but worth remembering it's still live.

**2. Components needing explicit dark handling vs. auto-inherit-for-free.** Grepped the actual codebase rather than guessing: 5 files use inline `style={{...}}` (`Avatar.jsx`, `Messages.jsx`, `MyGoals.jsx`, `Profile.jsx`, `Stats.jsx`) and 2 files use raw (non-token) Tailwind palette classes (`OutcomeBadge.jsx`, `StatusBadge.jsx`, 6 total hardcoded strings — `bg-yellow-100`/`!text-yellow-800`, `bg-gray-500`/`!text-white`, `bg-yellow-600`/`!text-white`, across `needs_reschedule`/`pending`/`no_answer`/`follow_up` states). Of the 5 inline-style files, most are purely geometric (width/height/fontSize — theme-safe by construction) or already token-based (`Stats.jsx`'s heatmap cell: `background: perfect ? 'var(--success)' : dialColor(d.dials)`) — but two are real, non-obvious landmines worth flagging specifically rather than a blanket "audit inline styles" line item: **(a)** `Avatar.jsx`'s `dialColor`-adjacent sibling problem — the 6 pastel `AVATAR_COLORS` (`#f6d5d5` etc., Prompt 491) are hardcoded hex, independent of theme by design (an avatar's chosen color should probably stay the same regardless of theme), but the initials text sitting on top of them uses the token class `text-fg-primary` — currently near-black (`#0f1f1b`), hand-verified in Prompt 491 at 12.2–14.4:1 contrast against all 6 pastels. If dark mode redefines `--text-primary` to a light color (the standard approach), that same class would flip the initials to light-on-light-pastel and destroy the contrast Prompt 491 specifically verified — this needs either the avatar to pin its own text color independent of the theme token, or the pastel swatches themselves to shift in dark mode. **(b)** `Stats.jsx`'s `dialColor()` heatmap gradient hardcodes its low end as pure white (`const start = [255, 255, 255]`) blending toward accent blue — a light-mode-only assumption baked into the algorithm itself, not just a CSS class; on a dark card background this would render near-white heatmap cells at low values, breaking the intended low-to-high visual hierarchy. Needs a real branch (light anchor vs. a dark-appropriate anchor, likely `--bg-elevated` or similar), not a CSS override. The 2 badge files are simpler but still real work: 6 hardcoded Tailwind palette strings need either `dark:` variants or conversion to token-based colors with a genuine dark-appropriate value chosen for each (pending/no_answer's gray-on-white and needs_reschedule/follow_up's yellow-on-yellow both need real dark equivalents, not just inverted lightness). Everything else — the other ~33 components and 14 pages — inherits automatically once the 13 root tokens get dark values, since they're already 100% token-driven with zero raw color classes.

**3. Where the toggle lives.** `src/pages/Settings.jsx` already has a real settings section (Prompt 458's `TimezoneForm`, the same self-service-RPC pattern as `update_own_full_name`/`update_own_avatar_color`) *and* an explicit placeholder card whose current copy reads: *"Nothing else to configure yet — Restorix doesn't have a theme toggle or integrations built yet. This section will grow as real settings arrive."* This isn't a design decision to make from scratch — the codebase already named this as the intended home for exactly this feature.

**4. Persistence: system-detected default + persisted manual override, following the existing precedent exactly.** `profiles.timezone` + `update_own_timezone` RPC (Prompt 458) is the direct template: add a `theme_preference` column (`'system' | 'light' | 'dark'`, defaulting `'system'`) plus an `update_own_theme_preference` RPC following the same whitelisted-self-service-RPC shape every other per-user setting in this project already uses (`update_own_full_name`/`update_own_timezone`/`update_own_avatar_color`) — `profiles` has no general self-update RLS policy by design (confirmed precedent from Prompt 491's own investigation), so this is the only correct path, not a shortcut. On load: read `theme_preference`; if `'system'` (the default), follow `prefers-color-scheme` live via a media-query listener; if `'light'`/`'dark'`, force that regardless of OS setting. Same shape as most mature apps' theme settings (system/light/dark three-way), not a plain on/off toggle.

**5. Rough effort estimate.** Foundation (root dark-token values, `darkMode: 'class'` config, media-query-aware theme-context/hook, `theme_preference` migration + RPC, Settings.jsx toggle UI): a genuinely self-contained unit of work, the majority of total effort. Auto-inheriting components/pages: near-zero marginal cost each, but all ~16 pages still need a real visual QA pass in dark mode since "should inherit correctly" and "actually looks right" aren't the same claim — several pages use `bg-elevated`-on-`bg-surface` layering for visual hierarchy (cards, tables) that needs eyeballing once real dark values exist, not just assumed fine. Explicit-fix items: `Avatar.jsx` initials-contrast fix (small, self-contained), `Stats.jsx` `dialColor()` dark-aware anchor (small, self-contained), `OutcomeBadge.jsx`/`StatusBadge.jsx`'s 6 hardcoded strings (small, mechanical once dark-appropriate values are chosen — the choosing is the actual work, converting the code isn't). No large unknowns found — this is a contained, well-scoped project given the token foundation already in place, not a ground-up rebuild.
